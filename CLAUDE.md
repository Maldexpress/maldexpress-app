# Project brief for Claude Code

## What this is
Maldexpress: a marketplace + delivery app for the Maldives. Three portals in one app — customer (public browsing), business (store management), delivery (job pickup). Currently a single self-contained file, `index.html`, with inline CSS and vanilla JS. No build tooling, no framework, no npm dependencies yet.

## Current architecture (as of this file's writing)
- **Hosting**: GitHub Pages from `main` (root): https://maldexpress.github.io/maldexpress-app/ (not Render). Merging to `main` deploys.
- **State**: one global `state` object, re-rendered on every change via a hand-rolled `render()` dispatcher keyed on `state.role` and `state.screen`.
- **Data layer**: `DB` object (`businesses`, `items`, `orders`, `delivery`) synced to Supabase Postgres tables via `loadDB()` / `saveDB(part)`. `saveDB` currently does a full-array `upsert` per call rather than single-row writes — fine at this scale, but revisit if it grows.
- **Auth**: **Firebase Auth** (project `maldexpress`), email + password with email-link verification; `fbAuth` in index.html. Supabase only stores data: it is created with `accessToken` returning the signed-in Firebase user's ID token (third-party auth), so `sb.auth.*` is unavailable. Firebase tokens carry no Supabase `role` claim, so requests run as the `anon` role and every RLS policy / SQL function identifies the user with `public.app_uid()` (Firebase `sub`, only for this project's tokens with `email_verified`). User id columns are `text`, not uuid. Migration: `supabase/migrations/2026-11-08_firebase_auth.sql`. Edge functions verify Firebase tokens themselves (`create-order-payment`, `upload-item-photo`, deployed with JWT verification off). Sign-in / password reset by **mobile number** goes through the `phone-login` function (it reveals the email only after the password checks out, and sends reset emails itself); `resolve_login_email` is no longer callable from the browser. **Storage does not accept Firebase tokens** (no Supabase `role` claim), so product photos are uploaded through `upload-item-photo` (service role, into `<firebase uid>/…` in `product-images`), never `sb.storage…upload` from the browser. `state.authed / state.customerId / state.customerEmail` hold the session.
- **Styling**: "Bright lagoon" light theme (replaced the dark "Sea of Stars" glass, "Atoll", "Harbour signage" and the original glassmorphism). A Maldivian island in daylight: a lagoon-washed white ground (`--sand-bg` #F3F7F6; real sand `--island` only on the illustrated island), white cards with soft shadows (the class is still `.glass`), turquoise lagoon (`--lagoon-500`, alias `--plankton`) for what's selected or active, sunset coral (`--sunset`, alias `--night-coral`) for the order-moving action and prices (`--sunset` #E24A24 for buttons, `--sunset-dk` for price text, both pass WCAG AA). Product tiles are borderless: a tinted image tile with the name and price on the page. Colours are checked with axe-core (zero WCAG 2 AA violations); pinch-zoom is allowed. Form boxes use 13px text in 42px boxes (`max(13px, 1.06em)`); to stop iPhone zooming in on a tapped box, a script in <head> adds maximum-scale=1 to the viewport on iOS only (iOS still allows pinch-zoom; Android keeps the plain viewport). The home header has no text: a turquoise→ocean-blue lagoon with the logo mark (`BRAND_MARK_SVG`), bell and menu/avatar, an illustrated atoll scene (`HERO_SCENE_SVG`: palm island, a sailing dhoni that bobs, the sun) and the search, ending in a wavy shoreline (`.hero-shore`) instead of rounded corners. The hero search is a slim 44px white pill with the magnifier on the left and a ✕ to clear, next to a small **Categories** pill (`homeSearchRowHTML(where)`, `.cat-open-btn`: opens a drop-down list of categories right under the search row, `catDropHTML()` / `state.catDropOpen`, closed by tapping outside or by scrolling the page ~24px (`closeDropdownsOnScroll()`, which also closes the Buy now menu, notifications and the PC category menu; scrolling inside the list itself doesn't count), and shows the picked category's name). The Buy now / Auctions / Rentals switcher sits under the hero where All categories used to be (`listingSwitcherHTML('bar')` in `.cat-bar`, next to the active-category chip). On phones the hero scrolls up with the page until its search row reaches the top, then it locks there as a small sticky header in the same lagoon gradient (the small header takes over at exactly that spot; over the next `MINI_GROW` px the logo slides in beside the search and a shadow fades in, `--p` 0→1, `_miniP` kept across renders) with the logo, the same search and the Categories pill (`homeMiniHeaderHTML()` / `updateHomeMiniHeader()`, `#homeSearchMini`; `state.homeSwitcherOpen` is `'bar'` when the listing-type menu is open). Nothing may leave a `transform` on `#app`, or `position:fixed` headers stick to it instead of the screen. On PC the scene sits to the right of the search. Fonts: Bricolage Grotesque for headings (`--display`), Plus Jakarta Sans for body. On phones the tab bar is docked white at the bottom and popups slide up as white sheets. On screens ≥1024px (PC, `isDesktop()`) the **customer side is a shopping website** (`siteHeaderHTML()`, `renderDeskHome()`, `siteFooterHTML()`; `body.site-desk`): a top strip (sign in/register, Auctions, Rentals, Sell, Deliver, shipping note, notifications), a main bar (logo, big search with a category picker and Search button, Saved / Orders / Account / Cart), a row of listing-type and category links, then on Home a wide promo banner with arrows (`DESK_BANNERS`; no auto-rotate), Shop by category tiles, Today’s picks, Sell / Deliver promos, the product grid, and a link footer. The store and rider portals on PC use a sticky top navigation bar instead of the bottom tabs. Popups open as centred dialogs on PC. Colour tokens live in `:root`; old names (`--glass`, `--coral`, `--ink`, `--channel`, `--ground`, `--shallow`, …) are kept as aliases because inline styles in the script use them. Mobile-first, `--fs` CSS variable drives the user-adjustable font size (default 12px, which is also the smallest; the Settings slider goes 12–22px).
- **Opening ad** (Admin → Settings → Opening ad; `platform_settings.ad_enabled / ad_media_url / ad_media_type / ad_link / ad_seconds / ad_skip_after`): a full-screen picture or video (uploaded through `upload-item-photo`, which also takes MP4 / WebM / MOV up to 25 MB) shown to everyone each time the app opens (`maybeShowOpeningAd()` / `showOpeningAd()`), 10 s long, Skip unlocks after 5 s, optional Learn more link; never in the admin portal; Preview button in Admin. Migration: `supabase/migrations/2026-11-13_opening_ad.sql`.
- **Bestsellers = sales through the app only** (`item_sales()` security-definer SQL function → `DB.sales`, `loadItemSales()`, `unitsSold()`): units on orders that were delivered and paid in the app — Swipe, or a bank transfer whose slip was uploaded and confirmed in the app (`slip_confirmed_at` set). Deals or cash arranged outside the app, and rentals, don't count. Home's Buy now grid is sorted by it (`sortByAppSales()`); the heading is 🏝️ Atoll Bestsellers only when something has sold, otherwise 🐚 Fresh off the Boat; cards show "🔥 N sold" (`soldLabelHTML()`). Migration: `supabase/migrations/2026-11-13_item_sales.sql`.
- **Home shuffles on every new view** (`viewShuffle()` with `_homeSeed`, picked anew in `render()` whenever the view key changes: arriving on Home, or changing its listing type / category / search; plain re-renders such as the live refresh or tapping a heart keep the order). Shuffled: the Buy now / auction / rental grid (anything that has sold in the app still goes first, by sales, then the rest shuffled), Sunlit Picks, the category rows, the Categories drop-down / sheet and PC menu (Other stays last), the PC header's category links and the Every Island Aisle tiles. `seededRank()` is FNV-1a plus a final mix so similar ids spread out.
- **Home Top selling** shows 5 rows (`TOP_GRID_ROWS`, `topGridMax()`: 2 or 3 per row by width); the rest go into swipeable rows below, one per category with See all › (`moreRailsHTML()`, `.rail`), or one "More to explore" row if it's all one category.
- **Motion** (`applyReveal()`, called after every `render()`): cards, sections and rows (`REVEAL_SEL`; not ones taller than 70% of the screen, which could never reach the threshold and would stay hidden) slide and fade in as they scroll into view and fade out as they leave (IntersectionObserver, also inside side-scrolling `.rail`s); things already on screen don't replay when the same screen re-renders (`_rvSeen`). Photos fade in after loading with a shimmer (`.img-fade` / `.img-loading`), the hero scene drifts with scroll (`heroParallax()`), the Featured panel has a gold sheen, section titles a lagoon→coral accent, cards lift on hover and press in on tap, and screens fade in on change (`.screen-in`, opacity only, never a transform on a wrapper of fixed bars). Items inside side-scrolling rows (`.rail`, Sunlit Picks, the gallery) slide in sideways, and those rows have `overflow-y:hidden` so a swipe can never move the cards up or down. All of it is off with prefers-reduced-motion.
- **Main header picture** (Admin → Settings → Main header picture, `platform_settings.hero_image_url`, `heroAdminPreviewHTML()` / `onHeroFile()`): when set, the Home hero shows that photo (`.home-hero.has-photo`, dark gradient on top so the search stays readable) instead of the island drawing, and the PC banner uses it too; empty = the drawing. Migration: `supabase/migrations/2026-11-13_hero_image.sql`.
- **Delivery zone picker**: drawn as a ferry route (`zoneRouteHTML()` / `pickZone()`), stops in order Malé → Hulhumalé Phase 1 → Phase 2. A hidden input keeps the `#c_zone` / `#cao_zone` ids.
- **App icon / logo**: the logo mark (two waves and a sun on a turquoise→blue tile) is the home-screen icon: `manifest.webmanifest` + `icons/` (192, 512, maskable 512, 180 apple-touch, 32 favicon). Regenerate all sizes together if the mark changes. Pressing the logo anywhere calls `goHomeFromLogo()` (customer Home with search/filters cleared; store dashboard; rider jobs).
- **Super Admin portal** (`?admin` in the URL, `renderAdmin()`): same Bright lagoon look. White top bar with the logo (`adminGoHome()`), a Super Admin badge, the signed-in admin and Sign out; a lagoon Overview banner with stats (stores, Pro, riders, orders, transfers to check, category ideas, fees owed); sections Stores / Bank transfers / Swipe payments / Category ideas / Fees as a sticky side menu on PC and scrollable chips on phones; cards in a 2–3 column grid on PC. **Admin → Stores → tap a store** (`openAdminStore()` / `adminStoreView()`, `state.adminStoreId`): the store's contact buttons, counts (items of 150, Live, Waiting, Paused, Taken down), filter chips and search, then its items **grouped by category** (per category: Approve N waiting, Pause all). Each item shows its status and the actions that fit it: Approve / Reject (waiting), Take down (live or paused: `admin_reject_items` with the reason typed above, the store sees it and editing resubmits), Pause / Resume (`admin_set_items_paused`), ★ Feature / Unfeature (`admin_feature_item`), Delete (confirm sheet, `admin_delete_items`, skips items in use). Migration: `supabase/migrations/2026-11-14_admin_manage_items.sql`.
- **Categories are on demand**, not a strip at the top of Home: on phones the **Categories** pill beside the search opens a sheet (`sheetCategories()` / `categoryGridHTML()`, icons and names only, no item counts) and a chip shows the active category with ✕ to clear; on PC an **☰ All categories** button in the header's category row opens a drop-down grid (`state.deskCatsOpen`), and the Explore categories tiles sit near the bottom of Home.
- **My addresses** (customer menu → 📍 My addresses, `openMyAddresses()` / `sheetAddressBook()` / `sheetAddAddress()`): add, edit, delete and set a default per category (your addresses, other receivers, boats). Each address stores an **island** (atoll + island picker; Greater Malé also an area/zone). With no saved address the menu opens straight to the add form, Home shows an "Add your delivery address" prompt, and checkout says the address will be saved as the default. Checkout fills in the default address and destination (zone or island) **once per opening** (`_addrDefaultsApplied`), stays editable, and saves what was used as the new default. Migration: `supabase/migrations/2026-11-11_address_island.sql`.

Migration: `supabase/migrations/2026-11-13_item_reviews.sql`. Item → related item keeps Back history. Two columns with a sticky photo on PC.

## Business rules to preserve
- **Listing is free for every store, up to 150 items** (`STORE_ITEM_LIMIT`; `tierInfo()` now just returns that limit). No trial, no Pro tier, and no plan text anywhere (store home, My items, Upload a list, sign-up, settings, PC promos); at the limit My items says "You've reached the 150-item limit. Delete or replace an item to add another." The DB enforces it (`items_store_limit` trigger, `item_limit_reached`). Admin store cards show "n / 150 items" instead of Pro controls. The old Pro request / payment code is still in the file but nothing opens it. Migration: `supabase/migrations/2026-11-13_store_item_limit.sql`.
- **Island-wise delivery** (`routeFor()` in index.html, `orders.route`): stores and riders each pick an atoll + island (`ATOLLS`). Greater Malé (Malé, Hulhumalé, Villimalé) → Greater Malé uses the zone fees below (`male_zone`). Greater Malé → any island goes by boat (`boat_to_island`); an island store can deliver on its own island (`local`) or send to Malé by boat (`boat_to_male`), but never to a different island (blocked at checkout). For every non-zone route the store sets the delivery charge when it approves (`approve_swipe_order(p_order_id, p_delivery_charge)`), which updates `delivery_fee`, `delivery_partner_payout` and `total`. Migration: `supabase/migrations/2026-11-08_islands.sql`.
- **Riders are island-wise**: a rider sees open jobs from stores on their own island (all of Greater Malé counts as one area), plus, while **online** with a GPS fix under 30 minutes old, jobs from stores within `NEARBY_KM` (20 km) of the store's saved location. New jobs alert inside the app (toast + vibrate + nav badge) on the 8 s live poll. Stores save their GPS location in Settings.
- **Island orders go to a boat**: at checkout, when the destination is another island and a Greater Malé store is sending it by boat (or no island is picked yet), "Deliver to" switches to **Deliver to a boat** automatically (`applyAutoDeliveryTarget()` / `checkoutNeedsBoat()`), with a note; back to Greater Malé switches back. If every store in the order is on that island (local delivery) it stays on a person. Once the customer taps person/boat themselves, it isn't switched again for that checkout.
- Delivery fee is a **flat amount by zone**, not a percentage: Malé MVR 15, Hulhumalé Phase 1 MVR 20, Hulhumalé Phase 2 MVR 25. Chosen by the customer at checkout.
- **Buy now orders are paid by Swipe or bank transfer** (cash on delivery was removed). A store can list and sell **without Swipe**: it needs either a connected Swipe account or a bank account number (`bizCanTakeOrders()`). At checkout each store card offers Swipe and/or Bank transfer (`ckPayFor()`; transfer only if no Swipe, Swipe only if no bank account). Both start as `payment_status 'awaiting_approval'`; the store approves (`approveOrderRequest()`, setting the boat / island delivery charge) or declines (`decline_order_request`). Swipe: → `awaiting_swipe` → customer pays on a Swipe link created on the **store's own Swipe account** (edge function `create-order-payment`) → `swipe-order-webhook?business=<id>` → `paid`. Transfer: `approve_transfer_order` → `pending_transfer` → customer uploads the slip (amount and account number must match) → `slip_uploaded` → store approves the slip (`approve_order_payment`) → `paid`. A Buy now order can't go to a rider until it's paid (`buyNowNeedsPayment()`), and riders never collect cash for it; the store owes the rider the delivery fee after delivery. Migration: `supabase/migrations/2026-11-10_buy_now_bank_transfer.sql`.
- **Fees**: on a Buy now bank-transfer order Maldexpress takes 5% (`TRANSFER_FEE_RATE`, recorded by `approve_order_payment` when the slip is approved). **On Swipe orders** Maldexpress takes 5% of the order total; Swipe's 1% charge is split 1:1 between the store and Maldexpress. So per order the store owes Maldexpress `5% − 0.5% = 4.5%` (`platform_fee_due`) and keeps 94.5%. Swipe has no split-payment API, so fees are tracked per order and settled by an admin (Admin → Fees). Rates live in `SWIPE_FEES` (index.html) and the webhook — keep them in sync.
- **Upload a list of items** (Items → Upload a list, `sheetBulkItems()`): stores download a CSV template (`BULK_COLUMNS`, opens in Excel / Google Sheets), fill one item per row and upload it. Rows are checked with the same rules as Add item and the plan limit, previewed with problems shown, and only valid rows are added. Photos (`bulkPhotoFor()`): a photo the store chose for that row in the preview wins, then a web link or file name in the `photo` column (case-insensitive, extension optional), then, if the column is empty, a picked photo named after an item code in the name/details (e.g. `LL0010.jpg`) or after the item name. The preview shows each row's photo and how it matched, flags picked photos no row uses and photos shared by several rows (`bulkPhotoAudit()`), and has Change / Remove photo per row. No photo means it's added later in Edit item. Excel `;`/tab separators are accepted; .xlsx must be saved as CSV first.
- **Item options (attributes) for every category** (`items.options` jsonb, e.g. `{"Size":["S","M"],"Colour":["Red"]}`; `itemOptions()` / `parseOptions()`). Each category has suggested options (`CATEGORY_OPTIONS`: Fashion Size + Colour, Grocery Weight + Pack size, Electronics Storage + Colour, …) shown in Add / Edit item under Category (`optionsEditorHTML()` / `readOptionsEditor()`, switching suggestions with the category and keeping typed values), plus a free row for a custom option. On the item page the customer picks one value of each (`optionPickerHTML()`); Add to cart stays off until all are picked. Cart key `itemId::Colour=Red&Size=M` (`cartKey()` / `parseCartKey()` / `cartLinesFromState()`), so each combination is a cart line; stock is shared (`cartQtyForItem()`). Order lines are named `Item (Size M, Colour Red)` and carry `options`. A quick "+" on an item with options opens its page. List template: an `options` column (`Size: S, M; Colour: Red, Blue`), any column named after an option (`OPTION_ALIASES`: size, colour/color, weight, flavour, storage, …), or, if none, "Colour: red, blue" found in the details (`optionsFromText()`). Migration: `supabase/migrations/2026-11-11_item_options.sql`.
- **Managing listings** (My items → ☑ Select, `state.bizSelect` / `state.bizSel`): Select all or tap items, then Pause / Resume (`setItemsPaused()`, `items.paused`; paused items are hidden from customers by `isApprovedItem()` and the items read policy), Edit stock, price… (`sheetBulkEdit()` / `bulkEditApply()`: category, stock, discount, price ± %, free delivery, Mark out of stock) and Delete (`askDeleteItems()` / `sheetConfirmDelete()`). Edit item also has Pause and Delete. Deleting is refused for an auction with bids or a rental with upcoming bookings (`deleteBlockReason()` in the app, `items_delete_guard` trigger raising `item_in_use` in the DB).
- **Up to 5 photos per item** (`PHOTO_MAX`, `items.images` jsonb array; the first is the cover and is also `image_url`). Add / Edit item use photo tiles (`photoSlotsHTML()`, `_photoSlots`, ★ makes a photo the cover, ✕ removes it), uploaded one by one through `upload-item-photo` (`uploadPhotoSlots()`); open forms with `startAddItem()` / `startEditItem(id)`. The item page shows a swipeable gallery (`itemGalleryHTML()`: a scroll-snap strip `#galTrack_<id>`, swipe / arrows / thumbnails / ← → keys; `galScrolled()` keeps the thumbnails and "2 / 5" counter in sync without re-rendering, `restoreGalleries()` keeps the shown photo across renders; the arrows show on touch or hover and fade out after ~2 s, `galWake()` / `.gal.idle`). In the list template the `photo` column takes several names or links separated by `|` (`bulkExtraPhotos()`). Upload a list has an **Upload a .zip of photos** button (`#bulkZipFile`, zip-only picker so phones offer Files, not just the gallery) next to Or choose photos; unzipped in the browser (`photosFromZip()`, stored/deflate, `DecompressionStream`). All of a list's photos upload 4 at a time with one running count. Every photo is shrunk before upload (`shrinkPhoto()`: long side ≤ `PHOTO_MAX_SIDE` 1600 px, WebP at `PHOTO_QUALITY` 0.86, JPEG if the browser can't write WebP; small photos and ones that wouldn't get smaller are left alone), so the Add/Edit picker accepts photos up to 20 MB. Migration: `supabase/migrations/2026-11-11_item_manage_photos.sql`.
- **Seller picks option values by tapping**: each option row shows ready-made values (`OPTION_PRESETS`: sizes XS–3XL, colours, weights, storage, …) as chips plus "Add" for their own; chosen values sit in a hidden `data-opt-name` input that `readOptionsEditor()` reads.
- **Item approval**: every new item (Add item or Upload a list) is `approval_status 'pending'` and hidden from customers until the super admin approves it (Admin → Item approvals, **store-wise**: one card per store, most items first, with the store's initial, item count, a peek of 5 thumbnails, Approve all / Reject all, and **Check one by one** to open that store's list with per-item Approve / Reject (`toggleApprStore()`, `state.admApprOpen`); `admin_approve_items` / `admin_reject_items`). The `items_guard` trigger forces every new item to pending, **even when the store owner is a super admin** (the column default is also `pending`; migration `2026-11-12_admin_items_need_approval.sql`), and stops sellers changing approval/featured columns; the items read policy only shows approved items to customers. Sellers can edit items any time; editing a rejected item sends it back for review. An auction's clock starts when it's approved. Customer lists use `isApprovedItem()`.
- **Featured**: limited spots (`platform_settings.featured_slots`, default 12; price `featured_price` MVR 50 for `featured_days` 3, all set in Admin → Settings along with Maldexpress's bank account). Sellers request it from Edit item (`sheetFeatureItem()` → `featured_requests`, bank transfer slip to Maldexpress; Swipe to Maldexpress shows as coming soon until Maldexpress's own Swipe is set up). The admin approves (`admin_approve_featured_request`, sets `items.featured_until`) or features any item directly (`admin_feature_item`, 0 days removes). Approval is refused when all spots are taken. The Featured section shows `featuredItemsNow()` (hour-seeded), re-shuffled on Home for every new view. Customers see it as **Sponsored** (heading and card badge; sellers and admin still call it Featured). It sits on a gold and light-blue panel (`.feat-panel`) with small gold-edged cards: phones show one row of 4 small cards on a band that runs edge to edge across the screen and swipe sideways for more (`.feat-grid`, one dot per 4; each card shows just the photo, heart and price, with any discount as a small "-10%" strip inside the bottom of the photo, `.img-disc`); PC shows a longer row of 6 (5 on smaller PCs) and slides for more (`.desk-row-feat`). Migration: `supabase/migrations/2026-11-11_item_approval_featured.sql`.
- **Swipe switch**: Swipe is offered (checkout, rentals, auctions, Pro) only when `platform_settings.swipe_enabled` is on (Admin → Settings) and the store connected it (`bizTakesSwipe()` / `swipeLive()`). Leave it off until the Swipe server keys are added.
- **Saves only touch your own rows**: `saveDB('businesses', [biz])`, `saveDB('delivery', [d])` — never the whole array (RLS rejects the whole batch if it includes someone else's row). Transfer slips go through `submit_transfer_slip(order, slip, amount, account)`, which checks status, amount and account on the server. Riders can only read waiting jobs they could take (`rider_can_see_open_order()`: same island / Greater Malé area, or online within 20 km). Migration: `supabase/migrations/2026-11-11_security_fixes.sql`.
- Connecting Swipe (client ID, client secret, webhook signing secret) is optional; without it the store takes Buy now orders by bank transfer. Credentials live in `business_swipe_accounts`, which has RLS with no policies so only edge functions can read them.
- **Rentals and auction wins** can be paid by Swipe (if the store has connected it), bank transfer, or cash **to the store** (`cash_on_pickup`). Riders never carry cash: the live `orders_insert_guard` / `orders_update_guard` triggers reject `pending_cash` for any method except `cash_on_pickup` (`cash_not_supported`). Swipe: a rental is inserted as `awaiting_swipe`; an auction win's `complete_auction_order` sets `awaiting_swipe` for `swipe`. Bank transfer: the customer uploads a slip whose amount and account number must match, and the store must approve it (`approve_order_payment`). Cash: the store marks it received. Swipe fees apply to these orders too.
- **The live database is ahead of this repo.** It has payment review / problem flags (`payment_review`, `flag_payment_problem`), store-set delivery charges (`set_delivery_charge`, `awaiting_delivery_charge`), checkout blocking for unpaid delivered orders (`customer_checkout_blocked`), and order guard triggers that were applied directly in Supabase. `supabase/live_functions_snapshot.sql` is a read-only snapshot (2026-11-08). Check it before replacing any live function.
- **Bank account required for stores and riders** (`bizHasBank()` / `riderHasBank()`, `requireStoreBank()` / `requireRiderBank()`): a store can't add items, upload a list or approve orders, and a rider can't go online, take a job or accept an offer, until they've added an account name + number; both homes show an "Add your bank account to start" card (`bankNeededCardHTML()`). Store accounts are on `businesses` (also shown to customers for transfers); riders' are in `rider_bank_accounts` (`saveRiderBank()` / `loadRiderBanks()`, `DB.riderBanks`), readable only by the rider, admins and stores the rider has delivered for, and shown on the store's Payouts so it can transfer delivery fees. The DB enforces it: `orders_rider_bank_required` (`rider_bank_required`) and `items_store_bank_required` (`store_bank_required`). Riders never collect cash and never owe a store. Migration: `supabase/migrations/2026-11-12_bank_accounts_required.sql`.
- **Store Payouts** (tab / menu → 💸 Payouts, `renderBizPayouts()`): only what the store owes — riders never collect cash, so there is no cash section. Two totals (You owe Maldexpress = unsettled `platform_fee_due`; You owe riders = `payout_status 'pending'` delivery fees), **Pay Maldexpress** (Maldexpress's bank account from Admin → Settings, "I've paid. Tell Maldexpress" opens a prefilled Live support ticket; the admin marks fees settled in Admin → Fees) and **Pay delivery riders** grouped by rider with contact buttons, per-delivery Mark paid and Mark all paid (`markRiderPaidAll()`, `mark_payout_paid`).
- **Customers see the delivery charge and can cancel before paying**: every customer order card shows Items / Delivery (zone, by boat, on the island; "Free", or "Added when the store confirms" while a boat / island order waits for the store's charge) / Total (`custCostRowsHTML()`). A Buy now order can be cancelled by the customer until they pay (Swipe: `awaiting_approval` / `awaiting_swipe`; transfer: `awaiting_approval` / `pending_transfer`, not once a slip is uploaded): **Cancel order** on the card and in the order detail → confirm sheet (`custCanCancel()`, `sheetCancelOrder()`, `cancelOrderByCustomer()`) → `cancel_order_by_customer(p_order_id)` sets `status 'declined'` + `cancelled_at`, so it ends like a declined order but shows **Cancelled** / "You cancelled this order" to the customer and "<name> cancelled this order" to the store. Migration: `supabase/migrations/2026-11-14_customer_cancel_order.sql`.
- Stores and customers can contact each other at any point (Call / WhatsApp / Viber buttons via `contactHTML()`) on the store's order detail, booking cards, and the customer's order detail.
- Store account number/name are only shown to the customer while it's their turn to pay or the slip is being checked (`pending_transfer` / `slip_uploaded`): not while the store hasn't accepted the order yet (`awaiting_approval`), and not after payment. "Slip sent. Waiting for the store to confirm the payment" shows only for `slip_uploaded`.
- **Bank slips leave the app once the payment is confirmed.** The app shows a slip only while it waits for the store (`slip_uploaded`); nothing about it is shown after confirmation. Confirming (order → `paid`/`settled`, booking charge → `collected`) stamps `slip_confirmed_at` (triggers `orders_slip_confirmed` / `bookings_slip_confirmed`). pg_cron runs the `purge-slips` edge function every 15 min: it moves each confirmed slip, exactly as stored (still encrypted for customer + store when it was), to the private `slip-archive` bucket (`orders/<id>.json`, `rental_bookings/<id>.json`) and clears it from the row (`slip_archived_at`, `slip_archive_path`); the triggers keep an archived slip from being written back by a stale save. A store that needs a slip asks through Live support. Migration: `supabase/migrations/2026-11-12_slip_expiry_support.sql`.
- **Live support** (menu → 🎧 Live support for customers, stores and riders; `openSupport()`, `sheetSupport()` / `sheetSupportNew()` / `sheetSupportTicket()`): tickets in `support_tickets` (topic, linked order/booking, status open / answered / closed) with messages in `support_messages`; the server sets who sent each message (`support_message_guard`). The super admin answers in Admin → Live support (`adminSupportTab()`), can close tickets, and for a slip request presses **Send the slip** (`support-send-slip` edge function, admin only, checks the order belongs to whoever opened the ticket): the archived slip is attached to the ticket and opened by the store's own app, so support never needs to see an encrypted slip. Open threads refresh every 10 s.

## Known follow-ups (not yet done)
1. **Split the single HTML file** into a real project structure (components/modules) once it grows further — it's still manageable as one file for now, but don't let it double again without restructuring.
2. **Slip uploads** are stored as base64 data URLs directly in the `orders.slip_url` column. Move to Supabase Storage once volume matters — cheaper and keeps table rows small.
3. **No business/delivery admin oversight** — e.g. no way to suspend a store, dispute a payment claim, or handle a customer complaint. Out of scope for MVP but worth flagging.
4. Payment for the Pro tier upgrade (`payForPro()`) is currently simulated client-side with no real payment gateway. Needs BML/real payment integration before launch.

## Conventions
- **Design taste skill:** `.claude/skills/maldexpress-taste/SKILL.md` holds the app's design rules (colours, type, spacing, island-voice headings, what looks cheap, motion, pre-ship checks). Follow it for any visual change.
- Keep everything mobile-first; this is meant to be used primarily on phones.
- Money is always Maldivian Rufiyaa (MVR); the `money()` helper formats it — don't hardcode currency strings elsewhere.
- Don't reintroduce `window.storage` or `localStorage`/`sessionStorage` for real data — Supabase is the single source of truth so the app works outside Claude's own preview environment.
